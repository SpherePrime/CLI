# Context Budget: стабильный кэш, MCP-группы, старение истории

Статус: проект. Системный промпт и шаблоны не меняются.

## Что уже есть

- Компактные карточки инструментов, `read_tool_documentation`.
- Проекция вывода: успех > 8 KiB и ошибки > 64 KiB уходят в артефакт, `read_tool_result`.
- Smart Tools: поиск `search_tools` / `search_mcp`, набор инструментов меняется по шагам.

## Где ещё теряются токены

1. Обычный режим отправляет карточки всех MCP-инструментов в каждом запросе.
2. Результаты инструментов до 8 KiB живут в истории до автосжатия, даже через 20 ходов.
3. Аргументы старых `write`/`edit`/`multiedit` содержат полный текст файлов.
4. Старые скриншоты и медиа остаются в каждом запросе.
5. Повторные чтения одного файла дублируются; чтения устаревают после правок.
6. Кэш промпта: в Smart Tools массив инструментов меняется → префикс (tools → system → messages) инвалидируется. Точки кэша — только system, последний инструмент и 2 последних сообщения.

## Этап 1. Измерения

- `context_breakdown.go`: категории `cache_read`, `cache_write`, `saved_by_projection`, `saved_by_aging`.
- Провайдерский usage: отдельно от оценки.
- Фикстура эталонной сессии (30 ходов, 3 MCP-сервера, браузер) для сравнения до/после.

## Этап 2. Стабильный префикс

- Smart Tools: найденные инструменты липкие на всю сессию, добавляются только между ходами пользователя, в конец списка.
- Anthropic: найденные инструменты отправлять с `defer_loading`, если провайдер поддерживает; иначе — липкий список.
- Точки кэша: system, конец инструментов, последнее сообщение предыдущего хода (стабильная граница), последнее сообщение.

## Этап 3. Старение истории (оба режима)

Новый `history_aging.go`, вызывается в `PrepareStep` после `projectToolMessages`. Полные данные в БД не меняются.

- Успешные результаты старше `aging_turns` (по умолчанию 3 хода) и больше 1 KiB → заглушка: инструмент, цель, размер, `artifact_id`.
- Ошибки старше порога → первые 2 KiB + артефакт.
- `view` файла, который потом изменён (filetracker) → «устарело, перечитать». Повторные чтения одного диапазона → остаётся последнее.
- Аргументы старых `write`/`edit`/`multiedit`: содержимое заменяется на `[N bytes, artifact]`, JSON остаётся валидным.
- Медиа: остаются последние 2, остальные → текстовая метка.
- Reasoning прошлых ходов не отправляется там, где провайдер это допускает.
- Граница старения сдвигается ступенькой: только в начале хода и только если экономия ≥ 16k токенов. Иначе кэш ломается на каждом шаге.

## Этап 4. MCP-группы в обычном режиме

- Сервер, чьи карточки ≤ 1500 токенов, остаётся inline.
- Крупный сервер сворачивается в одну карточку `mcp_<server>`: список имён инструментов и по строке описания, без схем.
- Вызов через `mcp_call(server, tool, arguments)`. Аргументы проверяются по канонической схеме, разрешения и хуки — по реальному имени инструмента.
- Схема конкретного инструмента — через существующий `read_tool_documentation`.
- Массив инструментов не меняется за сессию → кэш стабилен.
- Настройка сервера: `context: auto | inline | grouped`.
- `remote_workspace.go` получает ту же группировку для Desktop/SSH.

## Этап 5. Настройки и UI

- Config: `options.context.aging_turns`, `options.context.mcp_grouping`, `options.context.media_keep`.
- CLI: опции в `shellconfig/options.go`, пункт в палитре, сводка контекста с экономией и долей кэша.
- Desktop: в `ToolModeSetting.tsx` под «Стандартным» режимом — «Группировать MCP», «Сжимать старые результаты»; `toolTitle.ts` показывает реальное имя для `mcp_call`; переводы.

## Проверка

- Сериализованные запросы для Chat Completions, Responses, Anthropic, Google.
- Пары tool call / result сохраняются, системный промпт байт-в-байт тот же.
- Эталонная сессия: токены и cache hit до/после.
- Desktop local/SSH: одинаковое поведение.
